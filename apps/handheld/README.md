# Handheld — 폰이 유니티 카메라가 된다

폰을 들고 움직이면 유니티 카메라가 **그대로** 따라오고, 폰 화면에는 유니티가 본 그림이 뜬다.
버추얼 스트리머 컨텐츠용 손카메라. TASK-KAR-230.

```
폰 Chrome ──(wss: 포즈 60Hz + 스틱 30Hz)──▶ 유니티 WS 서버 ──▶ 카메라 포즈
    ▲                                                            │
    └──(wss: JPEG 뷰파인더 + 상태 1Hz)──── RT 렌더 ◀────────────┘
```

## 쓰는 법 — 조종석 하나로 끝난다

1. **유니티 열기** — `apps/handheld/unity` (Unity 6000.5.6f1 · **URP**)
2. 메뉴 **Handheld / 조종석** (`Ctrl+Shift+H`) — 씬이 없으면 알아서 짓는다
3. **「웹서버」 체크** → 포트 8842 가 열린다
4. **「공개 주소」 체크** → cloudflared 가 https 주소를 물어오고, 그 자리에 **QR** 이 뜬다
5. 폰 Chrome 으로 QR 을 찍고 **「시작 (6DoF)」** → ARCore 권한 허용
6. 폰을 들고 움직여라. 화면 아래 왼쪽 = 이동, 오른쪽 = 회전·높이

**Play 를 누르지 않아도 된다.** 서버·리그가 `[ExecuteAlways]` 라 씬을 여는 순간 살아나고,
조종석 창이 `EditorApplication.update` 로 리그를 돌린다(실측 틱 700~850 Hz). 손카메라는 유니티
창을 안 보면서 쓰는 물건이라 이게 기본값이다.

**리센터** = 지금 폰 자리를 씬의 `HandheldRoot` 자리로 맞춘다 (폰 하단 버튼 · 조종석 버튼 · `R`).
**원점으로** = 조이스틱으로 옮겨 다닌 `HandheldRoot` 를 처음 자리로 되돌린다. 편집 모드에서는
씬이 실제로 바뀌므로(Play 처럼 원복되지 않는다) 이 버튼이 되돌리는 손이다.

## 왜 WebXR 인가

「움직임을 **그대로**」의 벽은 **위치**다.

- `DeviceOrientationEvent` = 회전(3DoF)만. 가속도를 두 번 적분해 위치를 만들면 오차도 같이
  두 번 적분돼 몇 초 만에 무너진다 — 원리적으로 안 된다.
- **WebXR `immersive-ar`(ARCore)** 는 카메라로 특징점을 추적해 IMU 와 융합한다(VIO).
  세상이 기준자라 오차가 안 쌓인다. 앱 설치 0, https 만 있으면 된다.

그래서 6DoF = WebXR 이 본선, 자이로 3DoF 는 ARCore 가 없을 때의 폴백이다.
https 가 필수라 로컬 서버를 `cloudflared` 로 터널한다.

## 렌즈 — 줌과 초점

**렌즈는 물리 카메라로 말한다.** 줌 = 초점거리(mm) · 초점 = `focusDistance`(m) · 조리개 = f-stop.
셋 다 `Camera` 의 표준 필드라 **파이프라인을 안 탄다** — 빌트인이든 URP든 HDRP든 같은 값이다.
리그는 「어떤 렌즈인가」만 말하고, 흐리게 **그리는** 건 파이프라인 몫으로 남긴다. 그래서
URP 를 붙이든 빼든 `HandheldRig.cs` 는 안 바뀐다.

### 줌 — 폰의 W/T 로커

화면 오른쪽 시소를 위로 밀면 당기고(T) 아래로 밀면 넓힌다(W). 민 거리 = **속도**다
(방송 카메라가 그렇게 생겼다). 위쪽 빈 자리에서 **두 손가락 핀치**도 된다. `1×` 버튼이 리셋.

배율은 **로그 공간에서** 굴린다 — 1→2 와 8→16 이 같은 시간이 걸린다. 선형으로 이으면 망원
구간에서 혼자 가속하는 것처럼 보인다. 화각도 각도가 아니라 **`tan` 을 나눈다**
(`tan(fov/2) / 배율`) — 각도를 나누면 광학적으로 틀린 줌이 된다.

**줌에 딸려오는 두 가지** (빼면 망원이 못 쓸 물건이 된다):

- **손떨림이 배율만큼 커진다.** 각도 오차 1° 는 화면에서 배율만큼 커져, 1배에서 안 보이던
  떨림이 10배에서 화면을 흔든다. 그래서 보간 반감기를 배율에 비례시켜 「보이는 떨림」을
  일정하게 둔다(`zoomStabilize` — 렌즈 손떨림 보정이 망원에서 더 세게 도는 것과 같은 이유).
  무한정 늘리면 겨냥이 안 되므로 천장(`maxStabilizedHalfLife`, 기본 350ms)을 둔다.
- **스틱 회전이 배율만큼 빨라 보인다.** 10배에 90°/s 면 피사체가 눈 깜짝할 사이 프레임 밖으로
  나간다 — `zoomSlowsTurn` 이 배율로 나눈다.

### 초점 — 탭 포커스 · 랙 포커스

폰 화면을 **탭하면 그 자리**에 초점이 잡힌다. 탭 좌표는 화면 좌표가 아니라 **프레임 안 좌표**로
되돌려 보낸다 — 레터박스 여백과 세로그립 90° 회전을 안 빼면 엉뚱한 데 잡힌다.

| 모드 | 누가 잡나 |
| --- | --- |
| `AutoCenter` | 화면 한가운데를 계속 (기본). 탭하면 `Point` 로 넘어가 고정된다 |
| `Point` | 마지막으로 탭한 자리에 고정 |
| `Target` | 지정한 Transform 을 계속 (아바타 머리 등) — **방송에서 제일 안전하다** |
| `Manual` | 조종석 슬라이더가 정한 거리에 고정 |

초점이 옮겨가는 건 **디옵터(1/거리) 공간에서 잇는다** — 실제 포커스 링이 그렇게 돈다. 거리로
이으면 가까운 쪽에서 순간이동하고 먼 쪽에서 한없이 기어간다. `focusRampHalfLife` 가 랙 포커스
속도다 (0 = 즉시 = 기계적으로 불가능한 느낌).

초점 거리는 **광축에 투영한** 거리로 잰다. 직선 거리를 쓰면 피사체가 화면 가장자리로 갈수록
초점이 뒤로 밀린다.

### 흐림을 실제로 그리려면 — URP

초점 **값**은 파이프라인 없이도 나온다. **흐림**은 URP 가 있어야 한다.

이 프로젝트는 **3D URP 템플릿으로 새로 팠다**(2026-08-20). 빌트인이던 옛 프로젝트를 버리고
`Assets/Handheld/` + `Assets/StreamingAssets/handheld/` 를 `.meta` 째로 옮겼다 — GUID 를
그대로 들고 왔으므로 참조가 안 끊긴다. 옮길 자산이 그 둘뿐이라(씬·머티리얼·프리팹 0) 갈아타는
값이 거의 0 이었다.

**템플릿이 들고 오는 함정 둘**을 같이 고쳐 뒀다:

| 무엇 | 템플릿 값 | 고친 값 | 왜 |
| --- | --- | --- | --- |
| `activeInputHandler` | 1 (새 입력만) | **2 (둘 다)** | `Input.GetKeyDown` 이 Play 중 예외를 던진다 — `R` 리센터가 죽는다 |
| `runInBackground` | 0 | **1** | 창이 뒤로 가면 폰 화면이 얼어붙는다. 손카메라는 유니티 창을 안 보고 쓴다 |

색 공간은 템플릿의 **Linear** 를 그대로 쓴다(URP 기본). 옛 프로젝트는 Gamma 였으므로
뷰파인더 색이 전보다 조금 다르게 보인다 — 이건 URP 쪽이 맞는 값이다.

이미 URP 라 조종석의 **「URP 켜기」** 는 「이미 URP다」 하고 넘어간다. 빌트인 프로젝트에
이 리그를 떨어뜨렸을 때는 그 버튼 한 번이면 끝난다 — 패키지를 받고, 파이프라인 에셋을
만들어 그래픽스·품질 단계 전부에 꽂고, 씬에 글로벌 볼륨 + 보케 심도를 놓고, 카메라의
mm·m·f값을 그 볼륨으로 밀어 넣는 전달자까지 붙인다.

파이프라인을 아는 코드는 **`Assets/Handheld/Urp/` 한 곳**에 가둬 뒀다. 그 폴더의 asmdef 는
URP 패키지가 있을 때만 컴파일되므로(`versionDefines` + `defineConstraints`), **URP 가 없어도
나머지는 멀쩡히 돈다**. HDRP 로 갈 일이 생기면 그 폴더의 형제를 하나 더 두면 된다.

URP 보케는 초점거리를 1~300mm 로 자른다 — 망원 끝에서 흐림이 더 안 세지는 건 그 한계다
(닿으면 콘솔에 한 번 알린다).

| 파일 | 역할 |
| --- | --- |
| `Assets/Handheld/WsConnection.cs` | HTTP 101 핸드셰이크 + `WebSocket.CreateFromStream` 으로 프레이밍 위임 |
| `Assets/Handheld/HandheldServer.cs` | 폰 페이지 서빙 + WS + 포즈/스틱 파싱 + **좌표 변환(규약 단일 지점)** |
| `Assets/Handheld/HandheldRig.cs` | 포즈→카메라, 보간, 조이스틱, RT 캡처→JPEG(워커)→송신, 통계 |
| `Assets/Handheld/QrCode.cs` | 의존성 0 QR 인코더 (바이트 모드, ECC L/M) |
| `Assets/Handheld/Urp/` | **URP 가 있을 때만 컴파일되는 어셈블리** — 심도 전달자 + 배선 |
| `Assets/Handheld/Editor/HandheldUrpInstaller.cs` | URP 설치 버튼 (URP 타입을 안 쓴다 — 없을 때도 컴파일돼야 하므로) |
| `Assets/Handheld/Editor/HandheldWindow.cs` | 조종석 — 서버·터널 토글, QR, 손잡이 |
| `Assets/Handheld/Editor/HandheldSetup.cs` | 테스트 씬을 코드로 짓는다 (씬 파일은 커밋 안 한다) |
| `Assets/StreamingAssets/handheld/index.html` | 폰 페이지 (WebXR · 자이로 폴백 · 뷰파인더 · 조이스틱) |

**좌표계 변환은 `HandheldServer` 한 곳에서만** 한다 — 폰은 WebXR 원본을 그대로 보낸다.
WebXR(오른손·−Z 앞) → Unity(왼손·+Z 앞): `pos = (x, y, -z)` · `rot = (-x, -y, z, w)`.
축 하나를 뒤집으면 손잡이가 바뀌어 회전 방향도 반대가 되므로 쿼터니언의 `x·y` 도 같이 뒤집는다.

### 전선 위의 규약

| 방향 | 메시지 |
| --- | --- |
| 폰 → 유니티 | `p\|t\|px\|py\|pz\|qx\|qy\|qz\|qw\|fov\|aspect\|dof` (포즈, 화면 주사율) |
| 폰 → 유니티 | `j\|lx\|ly\|rx\|ry` (스틱, 30Hz) · `c\|recenter` |
| 폰 → 유니티 | `z\|배율` (줌, 미는 동안 30Hz) · `f\|u\|v` (탭 포커스, 뷰포트 0..1·아래가 0) |
| 유니티 → 폰 | JPEG 바이너리 (뷰파인더) |
| 유니티 ↔ 폰 | `k\|눈금` (왕복 재기 — 폰은 받은 것을 **그대로** 되돌린다) |
| 유니티 → 폰 | `s\|x\|y\|z\|yaw\|fps\|kb\|틱Hz\|캡처Hz\|배율\|mm\|초점m\|초점잡힘` (1Hz) |

상태 줄의 **칸은 뒤에만 붙인다** — 옛 폰 페이지는 앞 칸만 읽고 나머지를 무시하므로 안 깨진다.

네 곳의 큐가 전부 얕다(1~2장). 밀리면 **오래된 것을 버린다** — 실시간에서 밀린 프레임은
정보가 아니라 지연이다.

## 화면 비율 — 보이는 것 = 나가는 것

방송은 16:9 로 나가므로 **렌더도 16:9 고정**이 기본이다. 폰이 어떤 비율을 알려주든
(세로 0.46 · 가로 2.17 · 정사각 1.0) 렌더는 `1280×720` 하나로 나온다.

폰 화면에는 **레터박스**로 뜬다. 꽉 채우면(cover) 프레임 가장자리가 잘려 나가
「보이는 것 ≠ 나가는 것」이 되기 때문이다 — 뷰파인더는 송출 프레임과 같아야 한다.

### 주체가 다른 두 가지

| 무엇 | 누가 정하나 | 왜 |
| --- | --- | --- |
| **송출 비율** (16:9 / 9:16) | **조종석** (감독) | 방송으로 나가는 프레임. 카메라맨이 바꾸면 안 된다 |
| **그립** (눕혀 잡나 세워 잡나) | **폰** (카메라맨) | 손에 든 사람의 몸 편의. 나가는 그림과 무관하다 |

그립은 **시작 화면에서 한 번만** 고른다 — 「누워서」 / 「세워서」. 찍는 도중에 바뀌면
송출 프레임이 90° 튀어 방송 사고가 되므로, 세션 중에는 바꾸는 손잡이 자체가 없다.

**AR 세션은 진입 시점의 화면 방향으로 잠긴다.** 기기 자동회전을 켜도 세션에 들어간 뒤에는
페이지가 안 돈다 (2026-08-20 실기 확인: 가로로 들어도 `∠0 portrait`). 그래서 눕혀 쓸 거면
**눕힌 채로 시작을 눌러야** 한다 — 시작 화면이 지금 방향을 읽어 그 사실을 알려주고,
어긋나면 경고한다. 진입 순간의 실제 방향이 고른 것과 다르면 **현실을 따른다**
(가로로 들어갔는데 롤을 걸면 그림이 옆으로 눕는다).

- **누워서** — 롤 0. 16:9 가 그대로 꽉 찬다. 세로로 **2초 넘게** 들고 있으면
  「돌려서 잡아라」 안내가 뜬다 (카메라 워킹 중 롤이 세로를 스쳐 가는 건 의도된
  동작이라 그때는 안 뜬다).
- **세워서** — 폰이 `gripRoll=90` 을 보내 **카메라 롤을 90° 같이 돌리고**, 화면도
  −90° 돌려 되받는다. 둘이 짝이라 겨냥 방향과 그림이 어긋나지 않는다(롤은 전방 축
  회전이라 조준 자체는 안 변한다). 16:9 프레임이 폰 긴 쪽을 꽉 채운다.

가로로 들면 UI 도 가로에 맞게 옮겨간다 — 버튼은 오른쪽 위로 세로 배열, 통계 칩은
왼쪽 위, 스틱 구역은 아래 모서리. 세로 배치 그대로 두면 하단 버튼 바가 스틱 구역과
겹친다.

화면**만** 90° 돌려 채우는 길은 안 했다 — 카메라가 안 굴렀는데 그림만 돌리면 폰을
오른쪽으로 밀 때 그림이 위로 가는 **거짓 뷰파인더**가 된다.

대가가 있다. 세로 폰 비율일 때는 `332×720` 이라 6KB/장이었는데, 16:9 는 `1280×720`
= 픽셀이 4배라 **35KB/장**이고 인코딩이 병목이 된다.

| 경로 | fps | 대역폭 |
| --- | --- | --- |
| 로컬 720p 16:9 | 39.5 | 1.4 MB/s |
| 터널 너머 720p 16:9 | 31.5 | 862 KB/s |

무거우면 조종석에서 **세로 해상도**를 540·480 으로 내려라 (화질 ↔ fps 저울).

## 검증 (2026-08-20 실측)

- **폰 실기 6DoF 연결 확인** (Android Chrome + ARCore)
- 뷰파인더 **57~59 fps @720p** · 9 KB/장 · 첫 장 **26ms** (로컬), 터널 너머 34.6 fps · 254 KB/s
- 조이스틱: 이동 2.36m(예상 2.4) · 회전 87°(90) · 승강 0.96m(1.0) · 놓으면 표류 0
- 보간: 계단 +2m → 오차 **8mm** 수렴 · 정지 시 떨림 0
- QR: 버전 1·2·4·5 × ECC L/M 을 `qrcode-generator` 와 대조해 **코드워드 100% 일치**
- 좌표계 부호: 뷰파인더 캡처로 4방향 눈으로 확인 · 경로 탈출 404
- **데드맨**: 스틱을 쥔 채 연결을 끊고 5초 — 여분 이동 0.02m (고치기 전 계속 밀렸다)
- **16:9 고정**: 폰 비율 0.46·2.17·1.0 모두 1280×720 으로 렌더

## 튐·표류를 잴 때 — 포즈 기록

조종석 **「포즈 기록」** 을 켜면 `<프로젝트>/HandheldLogs/` 에 CSV 두 벌이 쌓인다.
같은 순번(seq)으로 **세 단계**를 나란히 적는다:

| 단계 | 뜻 |
| --- | --- |
| `raw` | 폰이 보낸 줄 그대로 (WebXR 원본, 우리가 손대기 전) |
| `conv` | Unity 좌표계로 옮긴 뒤 (부호만 바뀐 순수 변환) |
| `shown` | 리센터·보간까지 먹인 뒤 (실제로 카메라가 선 자리) |

```bash
node apps/handheld/pose-analyze.mjs <HandheldLogs 폴더>
```

**raw 에서 이미 튀면 ARCore/폰, shown 에서만 튀면 우리 코드다.**

### 망이 만든 지연도 같이 잰다

`pose-*.csv` 에 네 칸이 더 붙는다 — 「튐이 망 탓인가」를 가르려고 있다(그 답이 WebRTC 로
갈지 말지를 정한다).

| 칸 | 뜻 |
| --- | --- |
| `gap_ms` | 이 포즈가 앞 포즈보다 몇 ms 늦게 **도착**했나 (우리 시계) |
| `phone_gap_ms` | 폰은 몇 ms 간격으로 **보냈다**고 말하나 (폰 시계) |
| `jitter_ms` | `gap - phone_gap` = **망이 만든 변동** |
| `rtt_ms` | 왕복 시간 |

두 시계는 원점도 걸음도 다르지만 **각자의 간격끼리 빼면** 그 차이가 사라진다 — 폰이
균일하게 보냈는데 도착이 들쭉날쭉하면 `jitter_ms` 에만 남는다. 시계를 맞출 필요가 없다.

왕복도 같은 원리다. 유니티가 자기 시계 눈금을 보내면 폰은 **아무 계산 없이 그대로**
되돌리고, 유니티가 같은 시계로 두 번 잰다. 절대 문턱(몇 도·몇 ms)을
안 쓴다 — 그 값은 기계를 탄다. 같은 기록 안의 **중앙값 대비 배수**로 잰다.

판정기 자체는 답을 아는 합성 로그 5벌로 검증했다 (폰 원본 / 우리 코드 / 짐벌 지지 /
대조군 없음 / 자발 이동). 대조군이 없으면 「기각」이 아니라 **CANNOT-RUN** 을 낸다 —
전부 가파른 자세만 담긴 기록은 짐벌 가설을 반증할 수 없다.

**잴 때**: 증상이 난 구간을 짧게 · 가파른 자세와 완만한 자세를 **둘 다** 담고 ·
표류를 재려면 스틱에서 손 떼고 폰을 내려놓은 채 몇 초.

## 아직 안 한 것

- **좌우 회전이 가끔 튄다** (2026-08-20 폰 실기에서 관측, 원인 미확인)
- **조이스틱 조작감이 애매하다** — 레퍼런스 조사 필요 (속도·데드존·가감속 곡선)
- 인증 0 — 주소를 아는 사람은 누구나 붙는다. 토큰 게이트 필요
- 남은 포스트FX(흔들림·셔터·폰카 룩·노출) = 아직 범위 밖
- **줌·초점은 폰 실기에서 아직 안 재 봤다** — 코드만 섰다
- **전송이 제1 병목이다.** 포즈와 뷰파인더가 WS 하나·TCP 하나를 같이 탄다 — 영상이 업링크를
  채우면 포즈가 그 뒤에 줄 서서 **방송에 나가는 카메라가 늦고 튄다**. 카메라맨이 원격이면
  이게 제일 큰 문제다. 갈 곳 = **WebRTC** (영상 H.264/NVENC + 포즈 DataChannel 로 채널 분리,
  대역폭 1/8, 혼잡제어가 알아서 낮춘다). 그전에 `HandheldLogs` 에 도착 지터·RTT 를 넣어
  「튐이 망 탓인지 우리 코드인지」부터 재야 한다
